# Local native GPU / YuNet — 2026-11-11

CUDA and native WebGPU both execute YuNet correctly on the local RTX 4080.
CUDA reduces measured host-to-host forward latency from 5.90–5.98 ms on one CPU
thread to 1.025–1.027 ms. Native WebGPU measures 5.93–6.01 ms in this configuration.
This qualifies raw runtime execution on one Linux host. GPU executable packaging,
GPU-resident I/O, captured execution, NMS and crop equivalence remain unqualified.

## Configuration and checks

Measured on i265: Intel Core Ultra 7 265K, RTX 4080, NVIDIA driver 595.99.02.
ORT GPU 1.31.1 / source `6af1a932e`, native WebGPU plugin 0.5.0, NumPy 2.5.4,
Python 3.12.14, zenbench 0.1.10. Actual library hashes, dependency listings,
package versions and host topology are retained in the packet.

The native WebGPU plugin uses Dawn and Vulkan on this platform; this is separate
from Rust wgpu. See the [official WebGPU EP documentation](https://onnxruntime.ai/docs/execution-providers/WebGPU-ExecutionProvider.html).
CUDA uses device 0, TF32 disabled, a 1 GiB ORT GPU arena limit, heuristic cuDNN
algorithm search and `cudnn_conv_use_max_workspace=0`.
WebGPU explicitly selects NVIDIA vendor `0x10de` / device `0x2704`, NHWC layout,
basic validation and capture disabled. Computational CPU fallback and Python EP
retry are disabled. ORT profiling records the model math nodes on the requested
GPU provider. Intel render access fails for the ordinary user; Intel was not
included in the comparison. Windows GPU, Mac GPU and other adapters are untested.

All arms use the original ONNX model, SHA256
`8f2383e4dd3cfbb4553ea8718107fc0423210dc964f9f4280604804ed2552fa4`, loaded from
memory, with `ORT_ENABLE_ALL` and one intra/inter-op thread. Provider-specific
optimizations differ. This CPU baseline is measured here, rather than borrowed
from the earlier reduced executable's different model serialization/configuration.

Four fixed 640×640 FP32 BGR fixtures: the seed-911 diagnostic plus the three
existing DEV photo tensors from the reduced-Web experiment. The photo tensor
bytes, source identities and owned resize provenance are unchanged and retained
in `assets/photo-provenance.json`. No images were opened in model context, and no
new labels, training admissions or paid model API calls were made.

Each invocation excludes session construction, input preparation and three warm
forwards, then reports three batches of ten forwards. `Session.run` returns
CPU-visible NumPy outputs: the measured boundary includes upload, readback,
output allocation and destruction. It measures completed forward work, rather
than asynchronous submission. Preprocessing, NMS and crops are excluded.

The unchanged checker requires all 134,400 finite FP32 values per fixture and
`abs(candidate-reference) <= 1e-5 + 1e-5*abs(reference)`. Both GPU arms pass all
4/4 fixtures and 4/4 paired blocks per fixture. Largest absolute differences
across the primary checks are **4.5299530029296875e-6 CUDA** and
**4.887580871582031e-6 WebGPU**, with zero tolerance violations. GPU outputs are
not bit-identical to CPU; the A/A CPU comparisons are bit-identical.

## Profiling and the bounded cache check

Separate Nsight Systems 2025.5.2 traces retain actual CUDA kernel/memory activity
and Vulkan API activity. The unprofiled paired timings above do not use Nsight's
instrumented timing. Nsight's temporary stream paths were verified under the
task's disk scratch directory; final reports and SQLite exports are retained.

The CUDA trace contains 304 forwards plus session initialization. Device kernel
durations total 156.893468 ms; device memory-operation durations total 92.181419 ms,
including 79.449614 ms host-to-device and 9.329989 ms device-to-host. CUDA API
durations include 171.859522 ms in `cudaMemcpyAsync`, 116.891143 ms in kernel
launches and 81.197682 ms in library loading. These aggregates include startup
and can overlap; they are not additive end-to-end latency or steady-only metrics.

The WebGPU Vulkan trace contains 4,069 `vkAllocateMemory` calls and 4,069
`vkFreeMemory` calls. They account for 32.2% and 56.6% of Vulkan API time,
respectively. Its GPU-marker report is empty: no GPU-marker duration claim follows
from that report. Device selection, strict fallback policy and ORT node placement
separately establish the requested GPU execution. A raw-trace audit additionally
finds **53,999 positive-duration `VULKAN_WORKLOAD` records**, all on GPU 0.
Joining `gpu` to `TARGET_INFO_GPU.id` maps them to the **RTX 4080** at PCI
`0000:02:00.0`. This is recorded hardware workload evidence, separate from CPU
API timings and provider registration. All 53,999 records have null `textId`;
Nsight's installed `vulkan_gpu_marker_sum.py` filters `WHERE textId IS NOT NULL`,
which explains its empty summary. No labeled GPU-range duration is claimed.

`sudo perf record` captures 1,397 samples in a separate WebGPU run. The report
attributes 38.28% of sampled core-cycle weight to NVIDIA `osDevReadReg032`, with
memory-unmap/free and firmware-polling paths in its call stacks. This profiles
the whole process, including initialization and 900 timed forwards; it is not
a per-forward cache-miss or GPU arithmetic measurement. That run also changes
the input buffer to photo00 in the same session and passes the CPU reference
check, max absolute difference 4.172325134277344e-6.

One secondary test sets all four documented WebGPU buffer-cache modes to
`bucket`. All four fixtures and blocks pass the same numerical gate. Latencies
remain 5.922–6.035 ms; paired changes versus that run's CPU controls are -2.02%,
+1.52%, +1.46%, +1.70%, with A/A changes -1.65%, +2.27%, +0.10%, +0.005%.
It provides no useful latency improvement. Allocation counts after that setting
were not profiled, so reduced allocation counts are not claimed.

Secondary resource line: `run-heavy: done rc=0 33s | peak-RSS 0.26GiB |
min-avail 22860MiB | peak-load 0.39`, 4 GiB cap. This arm set excludes CUDA;
the lower RSS is not evidence of a cache-induced memory saving.
Perf resource line: `run-heavy: done rc=0 9s | peak-RSS 0.30GiB |
min-avail 23071MiB | peak-load 0.45`, 4 GiB cap.

Enabling WebGPU graph capture through `Session.run` rejects the first warm run:
the Python API requires fixed device OrtValues and `run_with_iobinding`.
The rejected attempt is retained; no captured-performance claim or fixed-device
I/O implementation is provided by this probe. Its `--graph-capture` option is
a compatibility probe, not a working captured execution path.
